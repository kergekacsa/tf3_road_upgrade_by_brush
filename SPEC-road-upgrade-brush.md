# Spec: brush street upgrade for Transport Fever 3

## Outcome

The player paints a brush over street segments, sees them highlighted, picks a road type and the same options as the single-click tool, and presses Upgrade. The tool upgrades up to 50 selected segments in one press. Today the street upgrade tool changes one segment per click.

The result is one new mod, `kacsa_road_upgrade_brush`. It combines the single-click upgrader of Road Upgrade Suite with the brush selection of Bulk Bulldozer.

## Scope

In scope:

- The single-click street upgrader, with its current behaviour.
- A new brush upgrade tool: select with a brush, then upgrade by street template.
- Road type, alley trees, and noise barriers for the brush tool. Build steps 1 to 4 deliver these.
- Bus lane, tram track, catenary, and lock for the brush tool. Build step 5 delivers these. Bus lane and lock work in the game. Tram track and catenary are written again with the corrected lane write (build u) and are not yet tested in the game. The underground option of the single-click tool only switches the underground view on, so that underground roads can be seen and selected (the user's statement, accepted as fact). The brush has the same button (key `undergroundMode`, taken from the single-click tool's options) and reacts to the game's shortcut G.

Version 2 idea (not decided, not in the first version): extend the method to railroad tracks, that is, select tracks with the brush and upgrade them to a track type in one press.

Out of scope for the first version:

- One-way road types for the brush tool. The single-click tool keeps them.
- Upgrading tracks, stations, assets, or town buildings.
- Publishing on mod.io.
- More than 50 segments per press.

- The mod MUST contain exactly two tools in the road tools menu: the single-click upgrader and the brush upgrade tool.
- The mod MUST NOT contain a Bulldoze button or any removal code.
- The brush tool MUST upgrade a segment with `api.engine.util.proposal.replaceSegment(edge, template)` and send the proposal with `api.cmd.makeWorldBuildProposalCmd`.
- The brush tool MUST offer the six two-way road types, the alley trees option, and the noise barrier option.
- The brush tool MUST offer bus lane, tram track, catenary, and lock before the first version closes (build step 5). Each option MUST give the same result on a segment as the single-click tool: bus lane removes the car from the outer driving lane on both sides, tram track adds the tram, catenary adds the electric tram, lock sets `roadDevelopmentLocked`. The tool applies them by editing `laneConfigs` and the lock flag of the added segment of the `replaceSegment` proposal (`applyExtras` in `bb_upgrade.tl`). A road that already has the template and the extras is left alone. The brush tool MUST NOT send a proposal whose lanes or lock flag do not read back as meant (`applyExtras`). The brush tool MUST have the single-click tool's Underground button (key `undergroundMode`). When it is on, the brush shows the underground view and selects tunnels. The shortcut G (input action `IA_UNDERGOUND_MODE_TOGGLE`) MUST switch it, and the button MUST follow (the menu changes its param `undergroundMode` on the event `streetBuilderRequestUnderground`). When it is switched off, the underground view MUST be off again and the brush MUST work as before.
- The brush tool MUST NOT offer the two one-way road types.
- The brush tool description MUST say that one-way road types exist only in the single-click tool.
- The selection cap MUST be 50 segments, and the command budget per press MUST be 50 (one command per segment).
- The brush tool MUST keep the bulldozer's selection rules: it skips other players' roads, construction parts, industry roads, and gone entities. It allows town-owned and unowned roads.
- While the underground view is on, the brush MUST select tunnels only and MUST NOT select roads on the ground (filter field `surface` false, reason `surface`). While it is off, tunnels are not selected (reason `underground`).
- The brush MUST NOT select a stand-alone tram track, that is a street none of whose lanes carries a car, a bus, or a truck (`isTramOnly` in `bb_gather.tl`, reason `tram_only`). A road that has tram tracks besides its vehicle lanes is selected as before.
- A road MUST be selected when the brush circle touches it (the curve of the road comes within the radius of the circle), as in Bulk Bulldozer. This holds for the hover preview, for a painted stroke, and for the Shift stroke that removes from the selection. A road is not required to have both end points inside the circle.
- The brush tool MUST remove the filters for tracks, stations, assets, and town buildings.
- The brush tool MUST check the hard rules again on fresh engine reads right before each command.
- The brush tool MUST offer the toolbar choice "Remove buildings in the way", on by default. When it is on, the commands use a context with `gatherBuildings` and `gatherFields` set, so a road that a building blocks is upgraded and the building is demolished, as the single-click tool does. When it is off, such a road is skipped and the game's message is shown. In the log of the second test, 6 of 15 roads failed with "Collision", the colliding entities were not roads, constructions, or nodes, and the game gathered 0 buildings; 4 more roads failed with "Unexpected parcel on a segment". Whether the option also removes the "Unexpected parcel on a segment" error is not verified.
- Error messages MUST be red and warnings MUST be yellow, in the game's theme colours (`Error` and `Warning` from `default_colors.gres`), set inline with `meta.styleSheet` (`brush_style.tl`). Errors: the notes about impossible combinations in the toolbar (for example alley trees on a country road), "Cannot upgrade", "Upgrade failed", "No answer from the game", and a result with no upgraded road. Warnings: "Nothing selected" after a press without a selection, and a result where some roads were upgraded and others skipped. Other text keeps its colour.
- The brush MUST leave a road alone, with no command and no charge, when it already has the target street template and, for a template that brings edge decorations, the same decorations. The result line counts these roads as "unchanged", not as skipped.
- The brush MUST send the commands for all roads first, then try each road whose command failed again. It MUST make two such retry passes, each after all other roads. A road that fails in all three attempts is skipped with the game's last message and stays selected. The result counts a road that a retry upgraded as upgraded.
- After a press, the roads whose command failed twice MUST stay selected and highlighted, and all other roads MUST leave the selection. Another press then tries only those roads. When no road failed, the selection clears.
- While an upgrade runs, a road MUST leave the selection and the highlight as soon as it is done: upgraded, already the target (left alone), or dropped by the hard rules. A road whose command failed stays selected. The status chip MUST show the progress while the upgrade runs: the head `Upgrading n of N` and a text bar with the percentage. A road counts once in a pass, also when its command failed, so the first pass reaches 100 %. When a retry pass starts, the chip MUST show `Retrying failed ones a/b` with the bar for the roads of that pass. The commit reports each road through the callback `onRoad` (`bb_status.tl`).
- Esc while an upgrade runs SHOULD stop the upgrade after the road in progress and leave the tool open, as the Clear button does (`cancelUpgrade` in the tool script). The game does not always give Esc to the tool (see Facts). When the tool is closed while an upgrade runs, the brush MUST cancel the upgrade after the road in progress, so that the game speed is set back. Without a running upgrade, Esc keeps its behaviour: it clears a selection first, and leaves the tool when nothing is selected.
- While an upgrade runs, the label of the Clear button MUST be `Cancel` and the status chip MUST show a third line under the progress line: `Cancel button stops the progress`. The cursor tooltip MUST say the same. Esc usually closes the tool (see Facts); the Cancel button stops the upgrade and keeps the tool open. The label MUST be in the warning colour of the theme (yellow).
- After a run, the status chip MUST show the end status in its head line as `X updated, Y failed` (X = roads upgraded, Y = roads whose command failed in all attempts). The head MUST be green (theme colour `Ok`) when X > 0, with the part `Y failed` in yellow when Y > 0, and red when X is 0 and Y > 0. The detail line lists the unchanged roads, other skipped roads, the main reasons of the failures, and the cost. After a cancel the head is `Cancelled · X updated` in yellow. The end status MUST stay until the next stroke, the next upgrade, or Clear, also while failed roads are still selected.
- The tool MUST show all its params in one window, the toolbar on the left (`location = Toolbar`). The menu shows params of the default location in a second window (a callout titled Settings); the tool MUST NOT use it. The order MUST be: radius, Underground, the road options (road type, bus lane, tram track, catenary, alley trees, noise barrier, lock, remove buildings, the red notes), the progress chip, the Upgrade and Clear buttons. The Clear label MUST be in the warning colour of the theme (yellow).
- The brush MUST send its commands only while the game is paused (game speed 0). When the game runs, the brush MUST pause it with the command `api.cmd.makeGameSetSpeedCmd(0)`, check the speed afterwards, and set the old speed back when the upgrade is done. Before every command it MUST check the pause again, because the player may unpause. When the game cannot be paused, the brush MUST send no further command, keep the roads selected, and show the red message "Pause the game first". (The game documents the speed command only for positive numbers, so this is the first test of speed 0.)
- The brush MUST wait 0.1 seconds after each sent command before it builds and sends the next one. The tool recipe drives the wait with `commit.tick()` on every step, and a new commit drops a wait that an unfinished commit left behind. The recipe MUST give a commit at least 120 seconds before it stops waiting for the result.
- The failure log line of a road MUST describe the road (normal, bridge or tunnel; template; edge objects; decorations; parcels left and right), so the reason for a repeated failure can be found in the log.
- The cost MUST be shown after the upgrade, from the cost the game reports for each command. A cost before the upgrade is not available.
- The cost preview SHOULD compute when a stroke ends, not on every refresh while painting.
- The brush tool MUST remember its settings during one game session: the radius, the road type, alley trees, noise barrier, "Remove buildings in the way", and the filters. Closing the tool and opening it again, or switching to another tool and back, keeps the last values. The values live in file-scope variables (`g_radius`, `g_toolParams`, `g_filterMem` in `brush_upgrade.script.tl`) and are used as the defaults when the toolbar is built. They are lost when the GUI is rebuilt, for example when another save loads. Not verified in the game: whether the menu builds the toolbar again on each open (build k logs 	oolbar built; remembered radius ...).
- The mod MUST keep the original authors' names in the headers of copied files.
- Publishing MUST NOT happen without permission from both original authors.
- The original Road Upgrade Suite MUST be switched off during tests. The real Bulk Bulldozer MAY stay on.

Defaults inherited from the bulldozer, not decided separately: paint a stroke, the selection stays highlighted, press the button to apply, Clear or right-click empties the selection, and there is no undo. While an upgrade runs, the Clear button reads Cancel and stops the upgrade after the road in progress; it does not empty the selection, so the roads that are not done stay selected. Without a running upgrade the button reads Clear and empties the selection. Roads already upgraded stay upgraded.

Open item: the underground (tunnel) filter. Keep the bulldozer default (off) until it is decided.

### Mod format (wiki.transportfever3.com)

- A mod folder holds `mod.json`, an optional `strings.json`, and `content/` for resources.
- `modId` MAY contain only `a-z`, `0-9`, and `_`. The recommended form is `<author>_<modname>`.
- `mod.json` hooks are `preRunScript`, `runScript`, and `postRunScript`, written as `<modid>::<file>@<function>`.
- Scripts are Lua, usually the Teal dialect (`.tl`). `local` is mandatory. Imports use `ug_require "<modid>::/path/file.tl" as TypeName`.
- A `.res.lua` file registers a resource. The tool resource has `type = "construction_tool"` and a `getDefinitionFn` that points to a script function.
- The mod uses `strings.json` for text, with keys per language. The wiki says missing keys fall back to English.

## Consequences of the decisions together

- The copy of the single-click tool has the same resource path and the same `rus_*` string keys as the original. Both mods cannot run at the same time.
- A cap of 400 selected segments with a command budget of 50 would highlight more than one press upgrades. The cap MUST be 50.
- The cost preview builds one proposal per road, so it is made when a stroke ends. The tool script no longer previews the cost while painting.
- A replaced segment may get a new entity id. The pre-send check then reports a neighbour as gone, and the upgrade is partial. The result line shows the counts.
- The brush has no one-way road types. The tool description and the README MUST say so.
- Build step 5 depends on a method that no known API provides (assumption 5). If no method exists, the first version cannot close as specified, and this spec needs a new decision.
