# Spec: brush street upgrade for Transport Fever 3

## Outcome

The player paints a brush over street segments, sees them highlighted, picks a road type and the same options as the single-click tool, and presses Upgrade. The tool upgrades up to 200 selected segments in one press. Today the street upgrade tool changes one segment per click.

The result is one new mod, `kacsa_road_upgrade_brush`. It adds a brush tool that combines the road types and options of Road Upgrade All in One with the brush selection of Bulk Bulldozer. The mod is independent of both and contains no single-click tool.

## Scope

In scope:

- A new brush upgrade tool: select with a brush, then upgrade by street template.
- Road type, alley trees, and noise barriers for the brush tool. Build steps 1 to 4 deliver these.
- Bus lane, tram track, catenary, and lock for the brush tool. Build step 5 delivers these. All four work in the game (user report, build u). The underground option of the single-click tool only switches the underground view on, so that underground roads can be seen and selected (the user's statement, accepted as fact). The brush has the same button (key `undergroundMode`, taken from the single-click tool's options) and reacts to the game's shortcut G.

Version 2 idea (not decided, not in the first version): extend the method to railroad tracks, that is, select tracks with the brush and upgrade them to a track type in one press.

Out of scope for the first version:

- One-way road types for the brush tool.
- Upgrading tracks, stations, assets, or town buildings.
- Publishing on mod.io.
- More than 200 segments per press.

The first retry of that road puts the asset groups in the `toRemove` list of its proposal; the last retry also sends the command with `ignoreErrors` set, as the Build Anyway mod does. Any other collision (a road, a construction, a node, a mix) MUST NOT be forced. The log line of such a retry names the number of asset groups and whether `ignoreErrors` was used. The brush MUST report such a road as failed, MUST keep it selected, and MUST NOT remove any house or lot for it: houses alone in the `toRemove` list do not help, and the game refuses lot entities there (see Facts). Errors: the notes about impossible combinations in the toolbar (for example alley trees on a country road), "Cannot upgrade", "Upgrade failed", "No answer from the game", and a result with no upgraded road. Warnings: "Nothing selected" after a press without a selection, and a result where some roads were upgraded and others skipped. Other text keeps its colour.

- The brush MUST send the commands for all roads first, then try each road whose command failed again. It MUST make two such retry passes, each after all other roads. A road that fails in all three attempts is skipped with the game's last message and stays selected. The result counts a road that a retry upgraded as upgraded.
- After a press, the roads whose command failed twice MUST stay selected and highlighted, and all other roads MUST leave the selection. Another press then tries only those roads. When no road failed, the selection clears.
- While an upgrade runs, a road MUST leave the selection and the highlight as soon as it is done: upgraded, already the target (left alone), or dropped by the hard rules. A road whose command failed stays selected. The status chip MUST show the progress while the upgrade runs: the head `Upgrading n of N` and a text bar with the percentage. A road counts once in a pass, also when its command failed, so the first pass reaches 100 %. When the tool is closed while an upgrade runs, the brush MUST cancel the upgrade after the road in progress, so that the game speed is set back. Without a running upgrade, Esc keeps its behaviour: it clears a selection first, and leaves the tool when nothing is selected.
- While an upgrade runs, the label of the Clear button MUST be `Cancel` and the status chip MUST show a third line under the progress line: `Cancel button stops the progress`. The label MUST be in the warning colour of the theme (yellow).

The keys are the input actions `constructOpt1` and `constructOpt2` of the game (the rotation keys; the file `settings_keys_v3.lua` binds them to M and N), so the player can rebind them in the game. Only the instance whose world layer is mounted acts (user request 2026-10-31, build at; needs a game test).
- After a run, the status chip MUST show the end status in its head line as `X updated, Y failed` (X = roads upgraded, Y = roads whose command failed in all attempts). The head MUST be green (theme colour `Ok`) when X > 0, with the part `Y failed` in yellow when Y > 0, and red when X is 0 and Y > 0. The detail line lists the unchanged roads, other skipped roads, the main reasons of the failures, and the cost. After a cancel the head is `Cancelled · X updated` in yellow. The end status MUST stay until the next stroke, the next upgrade, or Clear, also while failed roads are still selected.

The menu shows params of the default location in a second window (a callout titled Settings); the tool MUST NOT use it. The order MUST be: radius, Underground, the road options (road type, bus lane, tram track, catenary, alley trees, noise barrier, lock, remove buildings, the red notes), the progress chip, the Upgrade and Clear buttons. The Clear label MUST be in the warning colour of the theme (yellow).

When the game runs, the brush MUST pause it with the command `api.cmd.makeGameSetSpeedCmd(0)`, check the speed afterwards, and set the old speed back when the upgrade is done. Before every command it MUST check the pause again, because the player may unpause. (The game documents the speed command only for positive numbers, so this is the first test of speed 0.)

The tool recipe drives the wait with `commit.tick()` on every step, and a new commit drops a wait that an unfinished commit left behind. The recipe MUST give a commit at least 120 seconds without progress before it stops waiting for the result (each finished road restarts the time).

### Mod format (wiki.transportfever3.com)

- A mod folder holds `mod.json`, an optional `strings.json`, and `content/` for resources.
- `modId` MAY contain only `a-z`, `0-9`, and `_`. The recommended form is `<author>_<modname>`.
- `mod.json` hooks are `preRunScript`, `runScript`, and `postRunScript`, written as `<modid>::<file>@<function>`.
- Scripts are Lua, usually the Teal dialect (`.tl`). `local` is mandatory. Imports use `ug_require "<modid>::/path/file.tl" as TypeName`.
- A `.res.lua` file registers a resource. The tool resource has `type = "construction_tool"` and a `getDefinitionFn` that points to a script function.
- The mod uses `strings.json` for text, with keys per language. The wiki says missing keys fall back to English.

## Consequences of the decisions together

- Decision (2026-10-31): the copy of the single-click tool was removed, so that the original tool does not appear twice in the menu. The copy used the same resource paths and `rus_*` string keys as Road Upgrade All in One, so both mods could not run together. The brush stays independent: its copies of `config`, `options`, `rules`, `templates` (identical to the originals) and the icon moved to unique names (`road_upgrade_brush/rub_*.tl`, `rub_*` keys, `gui/road_upgrade_brush/brush_tool*.tga`). The hover probe in `proposal_probe.tl` was hooked into the removed `action.tl`; `probe.install` has no caller now.
- A cap larger than the command budget would highlight more roads than one press upgrades, so the cap and the budget MUST stay equal (both 200 since build ar).
- The cost preview builds one proposal per road, so it is made when a stroke ends. The tool script no longer previews the cost while painting.
- A replaced segment may get a new entity id. The pre-send check then reports a neighbour as gone, and the upgrade is partial. The result line shows the counts.
- The brush has no one-way road types. The tool description and the README MUST say so.
- Build step 5 depends on a method that no known API provides (assumption 5). If no method exists, the first version cannot close as specified, and this spec needs a new decision.
