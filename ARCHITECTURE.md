# Architecture

How the mod is built, which rules its code follows, and what the game does that the type definitions do not show. The player-facing behaviour is in `README.md`, the terms are in `CONTEXT.md`, and the reasons for the main design choices are in `docs/adr/`. This file sits next to the mod folder, so it is not part of the uploaded mod.

## Mod layout

All paths are under `kacsa_road_upgrade_brush\content\`.

The two `.res.lua` files are the two menu entries (roads, rail) of the same script. |

## Conventions

- The mod id is `kacsa_road_upgrade_brush`. It does not change.
- The mod MUST be independent: no mod dependency. It MUST work with and without Road Upgrade All in One (`road_upgrade_suite`) and Bulk Bulldozer switched on.
- Every file path and text key MUST be unique: `road_upgrade_brush/rub_*`, `rub_*` keys, `gui/road_upgrade_brush/`. Every global Teal type name carries the prefix `Rub`. Global names are shared by all loaded mods.
- Names that differ from Bulk Bulldozer, so that both run together: the log prefix `[BrushUpgrade]`, the events `BrushUpgrade.*`, the toolbar keys `brush_upgrade_*`, the recipes `BrushUpgradeAction` and `BrushUpgradeStatus`, and the tool id `brush-upgrade-tool`.
- Shared with Bulk Bulldozer by design: the toolbar style (the toolbar style rules of `brush_upgrade.css.lua` are skipped when Bulk Bulldozer or Smart Lanes is active; its rule for the button hints of a controller is always added), the developer master switch mod `square_sqperf_all` (it turns on the debug log of this mod), and the menu category `roads_tools` with order 5.
- The mod MUST keep the original authors' names in the headers of copied files, including `rub_types.d.tl`. The README names the copied texts of `strings.json`, which cannot carry a header.
- The mod MUST NOT add a single-click upgrade tool or a Bulldoze button.
- The mod folder MUST hold only files that the mod needs, with lowercase names. It MUST NOT ship image files of another mod.
- `strings.json` MUST hold every text that the code and `mod.json` pass to the translation, in the 12 languages of the game besides English. English uses the text as written in the code. A text with the same English words as a text of the game (`base.mo`) MUST use the game's translation. The exception is a word that is a mistranslation for this use (Off in Italian: the game says Mai, the mod says No).
- The names of the road types MUST be the names the game gives to its street templates.
- A text of the status chip MUST fit `status.MAX_CHARS` (36 columns, CJK characters count 2) in every language. The chip shows the short problem texts (`rub_chip_*`). The toolbar notes show the full texts (`rub_problem_*`).
- Every reason text of the commit MUST have an entry in the label table of `bb_status.tl`.
- A comment in the code MUST state only a contract, an invariant, a unit, or a constraint that holds now. Generated Lua is the same before and after a comment change.

## Game API

- `api.engine.util.proposal.replaceSegment(entity, streetTemplate?) : Proposal` refreshes a street or track segment. The type definition says "Use with caution" (`api\tealdef\api\engine\util.d.tl:987-991`). The brush upgrades one segment per road with it and sends the proposal with `api.cmd.makeWorldBuildProposalCmd`.
- The `StreetEdgeNodeModifier` (`base\tealdef\scripts\builtin.d.tl:157-187`) has `busLane`, `tramTrackType`, `symmetricLanes`, `overrideLaneConfigs`, `overrideEdgeDecorations`, `roadDevelopmentLocked`, and more. No API applies it to a proposal. The vanilla tools only fill it (`gui/construction/construction_react_util.tl:3181-3316`) and the engine applies it on click.
- `Proposal` is a userdata type with no way to merge two proposals. Its field `proposal : StreetProposal` holds `addedSegments`, `removedSegments`, and node and edge object lists. Each added segment has `comp : BaseEdge` with `roadTemplate`, `laneConfigs`, `edgeDecorations`, and `roadDevelopmentLocked`. The getters may hand out copies, so edits MUST be written back at every level.
- `replaceSegment` keeps the `edgeDecorations` of the old road, while the street template carries its own in `defaultEdgeDecorations`. The brush writes the decorations of the template.
- `makeProposalData` rejects the proposal of `replaceSegment` in every form (`bad argument #2 ... SimpleProposal expected, got Proposal`). So the cost is unknown before the command and known from its result.
- The base game tools change the template, not only the lanes: the bus lane tool gives the `_bus` template (`country_new_medium_bus`, outer lanes without the car), the tram track tool gives the `_tram` template (`town_old_large_tram`), and the upgrade mode with a tram gives `_tram_electrified` (`town_new_small_tram_electrified`). The vanilla proposal for a road with lots has the lot houses in `toRemove` (`moved` or `removed`, one construction each) and the moved ones again in `toAdd`; the game warns "N Buildings Will Be Moved; M Buildings Will Be Removed".
- A replacement with the template the road already has: the new segment keeps the lock flag, its lanes are rebuilt from the template (a tram track with catenary is gone), and it keeps the old `edgeDecorations`. So a change to the plain template does not remove alley trees by itself. Each replacement gives the road a new entity id.
- The vanilla proposal for one hovered road replaces many connected segments. `replaceSegment` replaces one segment per road.
- Tracks are street templates too (`roadType = "TRACK"`, one lane of width 4, `trackDistance` 5). The base game has `simple` (catenary from 1921), `standard` (from 1930), and `high_speed` (from 1980), each with a `_catenary` twin. `catenaryAdd` and `catenaryRemove` of a template name the twin.
- A track edge keeps its template in `BASE_EDGE.roadTemplate`. Its lane has the modes TRAIN and TRAM_TRACK, and with catenary also ELECTRIC_TRAIN and ELECTRIC_TRAM_TRACK. `BaseEdge.objects` holds `{entity, EdgeObjectType}` pairs (`SIGNAL`, `STOP_LEFT`, `STOP_RIGHT`).
- The game lists many more templates under `/track/`: the variants `_dv`, `_dvf`, `_dvp`, and `_dvs` of each base type, and the quiet copies that Station Noise Barriers (`station_noise_walls_1`) registers as `station_noise_walls_1::/quiet_tracks/<path>` with `noiseModifier` lowered by 0.65 for the track modules of stations with a noise wall. The `catenaryRemove` of a quiet copy names the plain base template.
- The game has a noise barrier for tracks as an edge decoration: `barrier_track_a.edge` (wooden, until 1939) and `barrier_track_b.edge` (concrete, from 1940), set on both sides as `{id, false}` and `{id, true}` in `edgeDecorations`. A change of the barrier alone is a full replacement of the track by the same template, so the game charges the template cost for it, also for Remove.
- A component that `api.engine.getComponent` returns, and a template that a repository returns, are views of engine data. After other commands ran, a view can read empty: a street template name read as `''` crashed the game with `ResTypeRep<StreetTemplate>::FindExisting: Resource not found` in `makeWorldBuildProposalCmd`. Code that keeps a value across commands MUST copy the value into plain Lua data first.
- A node entity can be replaced by another mod between two commands. Smart Lanes (`square_smart_lanes`, "Apply automatically to new roads" On) rewrote a junction node after the first large street joined a small one (lane count 1 to 3), the game logged `Apply: invalid entity: <node>`, and the next command that used the old id failed with an empty message. Code that builds in several commands MUST find a node by position for each command.
- A new node in a world build proposal needs an explicit `BaseNodeConfig` when its edges are streets with several lanes per direction (`town_new_large`). Without it the simulation thread asserts `it != components.end()` for component `BaseNodeConfig` on the new node, also when the whole grid is one command. A config with empty `laneConnections` and `crosswalks` is enough: the engine then makes the default routes. Grids of `town_new_small` finished without these configs. The mod `overpass_probe` states the same rule in a code comment.

- `BaseNodeConfig.userModifiedLaneConnections` is read-only in a script: a write fails with `no writable member 'userModifiedLaneConnections'`. A node config copy keeps the flag it was read with.
- `BaseNodeConfig.crosswalks` holds street segment entities. A vanilla junction of 4 streets listed its 4 segments, and a junction of 3 streets listed its 3. An explicit node config with an empty list gets no crosswalks from the game, although both town templates have `defaultWithCrosswalk = true`.
- The lane positions `lane0` and `lane1` of a `LaneConnection` are positions in `BASE_EDGE.laneConfigs` (pedestrian lanes included), counted from left to right when looking from the node along the street. That is the order of `laneConfigs` when the street starts at the node, and the reverse order when it ends there.
- A script MAY copy a `BaseNodeConfig` into a `BaseNodeLaneConnectionAndEntity` and set its `laneConnections` to a new Lua list of the `LaneConnection` objects that it read from the node. A Lua table in place of such an object is refused.

## Lanes and transport modes

- The transport mode numbers are PERSON 0, CARGO 1, CAR 2, BUS 3, TRUCK 4, TRAM 5, ELECTRIC_TRAM 6.
- The game gives out the modes of a lane as a table with the mode numbers 0 to 15 as keys and booleans as values. It takes them in as a complete list of 16 booleans, one per mode, counted from 1: the mode number plus one is the index. A table with only some indexes gives the lane the modes 0 and 1. A lane written back with the keys it was read with comes out with every mode one number lower.
- A wrong write gives a vehicle lane the cargo mode, and the game stops in its transport network (`TransportNetworkSystem.cpp IsValidTransition: Assertion 'person0 == person1' failed`). So the brush MUST NOT send a proposal whose lanes do not read back as meant.
- The lanes of the added segment per option (`<` and `>` are the two directions):

| Options on | Lanes |
|---|---|
| none | `<0+1 <2+3+4 >2+3+4 >0+1` |
| Bus lane | `<0+1 <3+4 >3+4 >0+1` (car removed from the outer driving lane) |
| Tram track | `<0+1 <2+3+4+5 >2+3+4+5 >0+1` |
| Tram track and catenary | `<0+1 <2+3+4+5+6 >2+3+4+5+6 >0+1` |
| Lock | `roadDevelopmentLocked true` on the added segments |
| Unlock | `roadDevelopmentLocked false` on the added segments |

## Failures

- Town roads with building lots on both sides fail with "Construction Not Possible; Unexpected parcel on a segment" on every press. The single-click tool upgrades many of them: its proposal puts the houses on the lots (constructions with one town building) in `toRemove` (removed) and `toAdd` (moved). `townBuildingSystem.getBuilding(parcel)` returns the TOWN_BUILDING entity, and its `construction` field is the entity of the `toRemove` list. The brush with the houses of the lots in `toRemove` still fails with "Parcel N for segment M is not removed". With the lot entities in `toRemove`, `makeWorldBuildProposalCmd` throws "Unknown exception" in `PreprocessProposal`. `parcelSystem.getParcelData(segment)` returns a native object with the lists `leftEntities` and `rightParcels`. Calling it crashes the game (an access violation in `TransportFever3.exe`). The mod MUST NOT call it. The houses of the lots are in `toRemove` and `toAdd` of the proposal of the base game tool. The retry of such a road is described in the next bullets.
- A road that an asset group blocks fails with the single message "Collision". An asset group is an entity with the component `ASSET_GROUP` (and no `BASE_EDGE`, `CONSTRUCTION`, or `BASE_NODE`). Putting it in `toRemove` upgrades the road. Roads that share one asset group make the removal list of a later road hold an entity that is gone, and the game throws "Unknown exception". So the list MUST be filtered with `api.engine.entityExists`. Other mods send the same proposal with `ignoreErrors` on (Build Anyway). Other "Collision" failures exist whose entities are not asset groups, and the brush does not force them.
- Further refusals ("Too Much Incline", "Construction Not Possible") are reported as failed with the message of the game.
- In the first retry of a failed road (attempt 1), with "Remove buildings in the way" on, the commit adds the lot houses around the road to `toRemove`. `probe.lotHouses` finds them through the octree (constructions with exactly one town building and no station, depot, or industry) and calls no `parcelSystem` function. The commit keeps only the houses that `api.engine.entityExists` still reports. More houses than the cap give an empty list. The first attempt and the second retry never get houses. A road that only asset groups block gets none: its removal list stays as it is without the lot houses. A press of tracks never gets them.
- With "Remove buildings in the way" on, at the first retry of a failed road that has no asset-group blocker, a neighbour that failed in the same pass and shares a node with the road is sent in ONE proposal with it (`pair_spike.tl`: `partners` finds up to three neighbours of the road in the order of the retry list, `merge` puts the street data of the second `replaceSegment` proposal into the first, and renumbers colliding temporary ids). The config of the node that the two roads share is reset to the default routes: its lane connections and its crosswalks are empty and the game makes the routes. A crosswalk list with temporary ids of new segments in the merged config gave no crosswalks, so the crosswalks come from the crosswalk pass (see the next bullet). The pair puts no lot house in `toRemove`: the game gathers the buildings itself. A success counts both roads as upgraded, and the neighbour sends no command of its own. When a pair command fails, the next neighbour of the road is sent at once (each pair once). When every pair of the road failed, the road fails as in a normal retry, and the neighbours take their own retries. An error while the pair is built is logged, and the road is retried alone. A malformed merged proposal can crash the game, so the marker line "pair spike: sending ONE proposal" is written before the command. The preparation of the pair runs in the same place as the read of the lot houses and has the same exception: it MAY run inside the callback of the pause command. Only pairs are merged, never a longer chain, and a press of tracks never forms a pair.
- A crosswalk pass runs after the last retry pass of a press, before the game speed is set back (`crosswalk_pass.tl`). Every junction that an upgraded road touched (both end nodes of every road that a command upgraded, single roads and pairs, read before the commands and recorded after the command succeeded; a road that failed touches nothing) gets a crosswalk on EVERY street segment of the node, also the roads that were not upgraded and country roads (`node_crosswalks.tl`, no filter: after an upgrade the streets at the node are often a country template, which the town-street rule of the console tool skips). The pass runs after the press and not after each command because Smart Lanes rewrites the config of a changed junction some time after a build, also while the game is paused, and overwrites a crosswalk that was written before it. When no touched node has `MIN_STREETS_FOR_CROSSWALKS` street segments, the pass ends at once. Otherwise it waits `CROSSWALK_SETTLE_SECONDS` before the first command, sends one all-streets command per junction in a round (a node with fewer than `MIN_STREETS_FOR_CROSSWALKS` street segments is skipped as "not_a_junction"), waits ONCE for `CROSSWALK_VERIFY_SECONDS`, then reads the config of every junction of the round back and compares it with the streets of the node. The junctions that are not complete go into the next round after another settle time, at most `CROSSWALK_ATTEMPTS` rounds. The steps of the pass run from the steps of the tool (`commit.tick`), so a tool switch or a cancel (Esc, Clear) ends the pass at once and leaves the junctions not yet done without crosswalks; the log then has the line "pass cut off by the cancel" with their number. The status chip shows "Placing crosswalks" with the number of settled junctions while the pass runs. When the game refuses the all-streets command, ONE command follows with the streets that have a pedestrian lane. A node is found by the position that was read before the commands, because another mod can replace a node. The log has the read back lines, one final line per node ("complete after K sends" or "INCOMPLETE ... missing streets") and a summary line. What the pass finds or the game answers never changes the result of the press and never stops the press, and a cancel stops the pass. The lines of the pass count as progress for the tool, whose timeout otherwise ends a press that shows none. A press of tracks has no pass.
- The read of the lot houses runs in the preparation of the command, outside a command callback. The exception: when the game runs and every road of the first pass fails before its command, the chain of the first retry starts inside the callback of the pause command, and the octree and `CONSTRUCTION` reads of `lotHouses` then run inside that callback.
- The result chip shows the hint "Turn on removing buildings" when "Remove buildings in the way" was off and a failed road carries the game message "Unexpected parcel" (English text: in another game language the text does not match and the hint stays away).
- Rare crashes occurred at speed 0, in the code of the game while it validated the proposal of a road with a large junction. The cause is not confirmed. No code of the mod reads parcels. The callback of a build command MUST read only the result data, the own `BASE_EDGE` of the road, the `ASSET_GROUP` component of the colliding entities, and the `GAME_SPEED` and `GAME_TIME` components of the world.

## Diagnostic log

- The option "Debug: upgrade log" (`rub_log` in `mod.json`, Off by default) switches the log lines on. With the option Off the probe reads no road and no proposal, except `lotHouses`, which the commit needs.
- `installApiCapture` hooks `getProposalStringsFn` of three base game tools (the street builder in upgrade mode, the bus lane tool, the tram track tool) and logs their proposal under the cursor. The hook reads components inside a callback of the base game, with the option On only.

## Menu, input, and instances

- The menu has two parameter windows. Params with `location = Toolbar` go to the toolbar on the left. Params without it go to a callout titled Settings.
- Slider params with `numbers` give the number (metres for the radius) to `onChangeFn`.
- The game registers the shortcut G only for tools whose action has a street, bulldozer, or similar builder (`construction_react_util.tl:3882-3895`). It answers the request `streetBuilderRequestUnderground` only for its own builder tools. The brush handles G itself and changes the toolbar button through the params API of the menu. It keeps that API from the call of `construction_react_util.getActionParams` (the 8th argument, `refSublistParams`; `installApiCapture` in the tool script).
- The Underground button only switches the underground view and the selection filter. It does not make roads tunnels.
- With a data layer picked in the layers menu, the world layer draws that layer (`preferredLayerConfig`) and no underground view, while the base tools show both. The base tools put `undergroundMode` on the builder of their `ConstructionAction`, and the brush has none. The mod does not add a `ConstructionAction` builder.
- The game gives Esc to its own menu when the keyboard focus sits on the toolbar, which is usually the case after a click on Upgrade. The menu then closes the construction mode, and the tool cannot take the key. The Cancel button works in every case.
- Mods cannot add input actions. M and N are the rotation keys of the game (`constructOpt1` and `constructOpt2`).
- In gamepad mode the menu renders the recipe of an entry with `isActive` false until the player activates the entry with `IA_APPLY` (`construction.tl`, `actionPresentState`). The component of the recipe sits inside the entry of the list that the D-pad moves through. `constructOpt1` and `constructOpt2` have the gamepad buttons `dpright` and `dpleft`, the buttons of `IA_NAV_RIGHT` and `IA_NAV_LEFT`, and `IA_UNDERGOUND_MODE_TOGGLE` has `leftshoulder` as its modifier, the button of `IA_TABLEFT` (`settings_keys_v3.lua`). The recipe MUST register its input actions only while `isActive` is true, as the base recipe does (`RegisterCustomSelectorBasedActionRecipe`). A player on a PS5 saw the menu navigation stay on the entry while the entry registered these actions without being active.
- The base tools get the move of the gamepad focus to the toolbar from the game: `getActionParams` adds `IA_OPTION2` (Triangle) to the input action table of `builtin.ConstructionAction`, and its handler fires the event `constructionMenuToggleBottomBarFocus` (`construction_react_util.tl`). The menu then moves the focus and fires `constructionMenuChangeFocusMode` with `"BottomBar"`, `"Params"`, or `"Action"` (`construction.tl`, `setFocusMode`). A custom action has its own `ActionDescriptor` and no `ConstructionAction`, so the recipe registers `IA_OPTION2` itself and fires the same event.
- Gamepad input actions reach the focused node and its ancestors. The menu leaves the focus on the entry of the tool, and the base game solves this for its inspector with a component that focuses itself on mount (`selector_react_util.tl`, `DefaultSelectorComp`). The recipe returns such a component (`BrushUpgradePadFocus`) in gamepad mode while its world layer is mounted, and it focuses the component again when the menu reports the focus mode `"Action"`. The mod Overpass Builder (`move_it_probe_overpass`, mod.io 6050917) uses the same technique, and its code comments are the source of the two statements about the focus. They are not confirmed by a test of this mod.
- A controller sends no mouse button event to the Selector. `IA_APPLY` and `IA_SELECT` (both Cross) make one stroke at the circle, which is the same code as a press and a release of the left button. The Selector reports Cross over a highlighted entity through `onSelect`, so that callback makes the same stroke in gamepad mode. The erase modifier `IA_PRECISION_MODE` is R1 on a controller. In gamepad mode the `ActionDescriptor` has `crosshair` on and `terrainCirclePolicy = "FocusSelection"`, as the base recipe has.
- While the toolbar has the gamepad focus, the handlers of the recipe answer `Disabled`, which leaves the buttons to the toolbar (`InputActionState` in `api\tealdef\api\gui.d.tl`).
- The entry of a custom action aborts the action in its step when `isActionActive(listIndex)` is false. That function compares the index of the selected definition with the position of the entry in the shown list, and the two differ when an entry before it is hidden (`construction.tl`). The menu order 5 keeps the brush before the year-gated entries of the base game. The code comments of Overpass Builder report that a higher order made the tool unusable on a controller.
- Ctrl + click is not usable for the middle-click copy: the game takes it as a multi-select of entities, opens the entity details, and closes the tool before the tool sees the click.
- The menu can create a second instance of the tool recipe, and the world layer that stays mounted can belong to the older instance. One game log showed the game sending the mouse events to the newer instance, whose ring has no cursor position. This cause of the stuck ring is not confirmed. `brush_layer.tl` keeps the owner of the layer. The newest instance passes its params to the owner, and only the owner steps and handles the clicks. A mouse event never makes another instance the owner while the owner is alive. An owner whose unmount callback was lost stays alive while its step runs, so the other instances drop their mouse events until the layer mounts again.
- The game sets the tooltip of a toolbar param once, when the component is created. It updates it only when the name, labels, numbers, or type of the param change (`construction.tl` `ConstructionParam`, `refTooltip`). Components are matched by position. A slider with the same name, labels, and values as the slider of another tool shows the tooltip of that tool. This is why the brush slider is labelled "Brush radius", not "Radius" (the label of Bulk Bulldozer).
- The stuck ring (the circle stayed fixed on the map after switching the Underground button or the map layers) also occurs in Bulk Bulldozer, which has the same layer flag, mount and unmount callbacks, and underground `LayerConfig` child.
